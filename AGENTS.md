Твоя задача — самостоятельно реализовать проект согласно требованиям ниже, принимая инженерные решения только там, где они не противоречат архитектуре и ограничениям проекта.

7. Запусти lint.
8. Запусти unit tests.
9. Запусти integration/e2e tests, относящиеся к изменению.

12. Обнови документацию при изменении поведения или архитектуры.
13. Только после полностью зелёных проверок переходи к следующему milestone.

Не останавливайся после создания файлов или написания кода. Проверяй реальное выполнение проекта.

## Критические архитектурные правила

BrowserMesh — НЕ обёртка вокруг Playwright MCP.

BrowserMesh — независимый multi-session browser runtime.

MCP является adapter/transport boundary, а не ядром приложения.

Playwright является browser adapter, а не частью domain layer.

Domain и application layers не должны импортировать Playwright.

MCP layer не должен напрямую манипулировать `Browser`, `BrowserContext` или `Page`.

Любое browser действие должно проходить через application/runtime services.

Не должно существовать глобальной `currentPage`, `activePage`, `currentSession` или аналогичного mutable singleton state.

Каждая browser operation должна явно адресовать session.

Параллельные разные sessions должны иметь возможность выполняться одновременно.

Операции одной session должны быть защищены от разрушительных race conditions.

## Не overengineer

Для MVP запрещено без реальной необходимости добавлять:

* Docker;
* Kubernetes;
* Redis;
* PostgreSQL;
* RabbitMQ;
* Kafka;
* NATS;
* microservices;
* distributed workers;
* authentication service;
* web dashboard;
* React frontend;
* external queues;
* cloud infrastructure.

Первый runtime должен работать локально в одном Node.js process.

Но архитектурные интерфейсы должны позволять заменить in-memory implementations позже.

## Контроль качества

Код должен:

* иметь строгую типизацию;
* не использовать `any` без документированной причины;
* корректно освобождать BrowserContext и browser resources;
* корректно обрабатывать ошибки;
* иметь deterministic tests;
* избегать shared mutable global state;
* не скрывать ошибки пустыми catch;
* не содержать hardcoded machine-specific paths;
* не хранить secrets/auth state в Git;
* корректно завершать runtime по shutdown signal;
* быть пригодным для open-source публикации.

Каждый публичный service/API должен иметь понятные contracts и predictable error behavior.
